# Session 1 — glyph data model: the storage layer, built out

## Todo status
`docs/future/CURRENT_TODO.md` → "Next Work To Do → Rune System": marked the glyph data model
(storage) done and expanded what is left under it. The old block was "Implementing Rune system /
passive runes / active runes / some of this might have been started by" — the trailing note was
guesswork about whether any of it existed, and now it does, so the block lists what is actually
outstanding: point allocation, the flat → percent → multiply resolve, the resource pools,
techniques on locomotion, and status effects.

Nothing was marked done that is not done. The data model has no reader yet, so none of the
runtime items were touched.

## What changed
**Where:** `Scripts/Glyphs/` — 7 files modified, 1 deleted, 12 added. Build verified via
`dotnet build Glyphwake.csproj`: succeeded, 0 warnings, 0 errors.

The glyph system was 7 files and 154 lines of which about 7 lines were executable logic. It was
a schema that described *what a glyph is* with no code that could read one. This fills in
everything storage needs so glyphs can be authored, and stops short of anything that casts.

### The three subclasses
`PassiveGlyphData` and `ActiveGlyphData` already existed. `TechniqueGlyphData` is new
(`Scripts/Glyphs/TechniqueGlyphData.cs`), because the design doc's third type is not a flag on an
active: a technique adds a capability that did not exist before (double jump, wall jump), rides
an existing input rather than a hotbar slot, and is never aimed. So it carries a
`TechniqueTrigger` (`Airborne` / `WallContact` / `HeldInput` / `Submerged`) where an active
carries a `GlyphTargetType`, and `CastTime`/`Cooldown` are absent because a technique does not
have them. When points are in a technique it is on, per the doc.

### Classification is now real
`Scripts/Glyphs/GlyphSchool.cs` and `GlyphElement.cs` are the doc's six schools and six
elements as enums. **Cause:** the code's `GlyphCategory` (Capability / Movement / Utility /
Attack / Summoning) predated `GlyphDecisions.md` and overlapped School — `Movement` is Flowing,
`Summoning` is Calling. Two axes describing the same thing is one more place for them to
disagree, so `GlyphCategory` is gone. School and element are separate questions anyway: the doc
says explicitly that school is "the essence of how it affects the world" and has nothing to do
with element, and element is what decides resistance.

They are enums rather than `GlyphTag`s because anything a *filter* enumerates has to be closed —
resistance tables, combo rules and passive filters all need to walk the whole set. A free-form
tag cannot do that. `Tags` stays for classification neither set covers.

### Tag matching was reference equality
`GlyphTag` gained a `StringName Id` (`Scripts/Glyphs/GlyphTag.cs:11`), and `GlyphData.HasTag`
plus `GlyphModifier.Affects` match on it. **Cause:** the old `PassiveModifier.AffectsTag` did
`TargetTags.Contains(tag)`, which is `Array<T>.Contains` — reference equality on the resource
instance. A tag authored in the editor and the same tag built in code would not have matched,
and duplicating a `.tres` would silently break every passive pointing at it. `Id` is separate
from `DisplayName` on purpose: the name is player-facing text and free to be reworded.

### Cost is a list, not a float
`ActiveGlyphData.ManaCost` / `ManaCostPerPoint` are replaced by `Array<GlyphCost>` with
`CostResource` (Mana / Health / Stamina), each entry carrying `Amount`/`AmountPerPoint` for an
up-front spend and `PerSecond`/`PerSecondPerPoint` for a drain. **Cause:** the doc says channels
cost per time used, and that some glyphs spend health as deliberate outliers. A single float
could not express "12 mana up front, then 4 stamina a second while you channel", which is what a
Searing Beam costs.

### The three missing axes
`GlyphCastMode` (Impulse / Focus / Channel / Ritual), `GlyphEffectMode` (Instant / Channel /
Anchored / OverTime), `GlyphTargetType` (Self / Single / Projectile / GroundPoint / Direction)
and `GlyphAffects` (flags: Enemies / Allies / Self / Terrain) are now separate enums. **Cause:**
the doc defines all four and the code had none of them — `CastStyle` conflated target type with
the shape of the effect. They are independent: a channel cast can leave an anchored totem
behind it, so `CastMode` and `EffectMode` are not one field.

`GlyphAffects` is `[Flags]` because a glyph may legitimately hit enemies and allies at once,
which a single enum value could not express.

### `StatKey` split by owner
`Scripts/Glyphs/StatKey.cs` now groups the glyph's own numbers (Damage, Radius, Range,
Duration, Cooldown, ManaCost, CastTime, Speed, JumpHeight, Knockback, ProjectileCount,
AreaOfEffect) separately from the caster's (MaxHealth, ManaRecovery, HealthRecovery, Stamina,
StaminaRecovery). **Cause:** one enum holding both is what let mana cost have two independent
scaling paths — a float on `ActiveGlyphData` *and* a `StatKey`. The comment on the enum said the
set is closed so "a modifier that names something outside it has no way to be applied"; it could
not have been applied correctly if it had two owners. ProjectileCount and AreaOfEffect are new
members because the doc's passive section calls out changing projectile count and area of
effect as things passives do.

### Passives are three lists, not one
`PassiveModifier` is deleted, replaced by `SelfStatModifier` (your own stat),
`GlyphModifier` (other glyphs, filtered by school/element/tag) and `PassiveTrigger` (an event
that spawns a payload). **Cause:** the doc gives these three targets explicitly and they are
genuinely different shapes. A `GlyphModifier` has a classification filter; a `SelfStatModifier`
has nothing of the kind, and putting one enum field on a shared type means every entry carries
a filter it cannot use. The old shared list also could not express an on-hit burn, which is not
a stat delta at all.

`GlyphModifier` filtering on an empty `Schools`/`Elements`/`TargetTagIds` means "all glyphs",
which is the doc's "All" case. **Note:** schools and elements combine as AND (must match the
school *and* carry one of the elements) while tags are OR — a glyph matching any listed tag
qualifies. That is a judgement call, not something the doc settles.

`ModifierOperation` gained `Percent`. The doc's flat → percent → multiply rule could not be
expressed without it, and `GlyphDecisions.md` already flagged the gap.

### Behaviour is a payload scene
`ActiveGlyphData` and `PassiveTrigger` both hold a `PackedScene Payload`, which the caster
spawns. **Decision:** behaviour does not live in the resource. The data says what a glyph is and
how strong it is; the payload node is what happens in the world, as an ordinary Godot scene the
artist can tune in the editor. A `GlyphEffect` resource with an `Execute()` method was the
alternative and would have meant a new C# class per effect — worse for authoring, though more
unit-testable. `StatKey` lookups are on both (`ActiveGlyphData.StatAt`, `PassiveTrigger.StatAt`)
so a payload and an active read their numbers the same way.

### Points are not stored on a glyph
Deliberately. `GlyphData` is an immutable shared `Resource` — one `.tres` is one object — so
allocated points stored on it would be the same for every player holding that glyph. The 100
point pool allocator (still a todo) has to key a player-owned loadout by resource path.
Recorded in `GlyphDecisions.md` "Not built yet" so it is not rediscovered later.

# Session 2 — scaling is per-glyph, not a shared linear formula (todo + worklog)

## Todo status
`docs/future/CURRENT_TODO.md` → "Next Work To Do → Rune System": added "cost and
passive-modifier growth still linear-only (scaling styles only on glyph stats, see
GlyphDecisions.md code notes)" so the remaining linear `PerPoint` code is not rediscovered as
a bug later. Nothing marked done — the loadout/stat resolver items are untouched.

## What changed
**Where:** `Scripts/Glyphs/` — 5 files modified, 4 added, 1 deleted. Build verified via
`dotnet build Glyphwake.csproj`: succeeded, 0 warnings, 0 errors.

The glyph's numbers scaled through hardcoded linear maths (`ScaledStat` = base + perPoint,
plus `CastTimePerPoint`/`CooldownPerPoint`/`DurationPerPoint` fields and trigger
`DurationPerPoint`), so every glyph scaled identically and the design doc's "different glyphs
will scale differently — not locked in to flat or exponential" was unimplementable.

### The scaling object
`GlyphScaling.cs` is the scaling entry the design calls for: it points at a `StatKey`, names a
`GlyphScalingStyle` (Linear / Quadratic / SquareRoot / Step, `Scripts/Glyphs/GlyphScalingStyle.cs`)
and carries the value; `StepSize` (default 1) completes Step. `GrowthAt(points)` dispatches on
style past activation — one glyph scales linearly while another accelerates, diminishes or
arrives in chunks.

### Base statistics split out
`StatValue.cs` is one base statistic (`StatKey` + value). `GlyphData` now holds
`Array<StatValue> BaseStats` + `Array<GlyphScaling> Scalings`, and `StatAt`/`TryStatAt` on
`GlyphData` are base-plus-growth through the shared `GlyphStats` static helper. **Why the
split:** base value and scaling curve are authored separately, and which keys a glyph has is
now deliberate — absence of an entry is how "zero for that mode" is expressed.

### The linear `PerPoint` fields are gone
`ActiveGlyphData` lost `CastTime`/`CastTimePerPoint`, `Cooldown`/`CooldownPerPoint`,
`Duration`/`DurationPerPoint` and `Range` — CastTime, Cooldown, Duration and Range are base
stats now (the existing `StatKey` members already named them). A Self target has no Range
entry and an Impulse has no CastTime entry; `StatAt` returns 0 for both, which is what the old
"zero for X mode" comments described. `ScaledStat` is deleted — its `TryValueAt` factor-out
became `GlyphStats.TryStatAt` on the shared helper, because 0 is a legitimate value and only
the boolean tells "no entry" from "explicit 0".

`TechniqueGlyphData` sheds its own `Stats`/`StatAt` (inherited). `PassiveTrigger` keeps its
own `BaseStats`/`Scalings` — it is not a `GlyphData`, and one passive can fire several payloads
with different needs — through the same helper.

### Still linear-only, deliberately not migrated here
`GlyphCost`'s `AmountPerPoint`/`PerSecondPerPoint` and `SelfStatModifier`/`GlyphModifier`
`PerPoint` are pre-style code. Cost and modifier growth are the loadout/resolver layer's
territory (next todo); recorded in the todo and in `GlyphDecisions.md` code notes.

## Docs updated

- `docs/design/Scripts.md` — `ScaledStat` rows replaced by `StatValue` / `GlyphScaling` /

# Session 3 — movement bugs: fall speed and the fixed capsule (diagnosis, no code yet)

## Todo status
No change to `docs/future/CURRENT_TODO.md` — neither bug is a tracked item; the fix is in
flight in the working session.

## What was found (nothing changed in the project)
**Where:** `Scripts/Player/PlayerController.cs`, `Scenes/Player.tscn`, `Scenes/Stickman.tscn`,
`Scripts/Core/PlayerRig.cs`. No file was modified — this session is the diagnosis only.

Two movement bugs, both reported after playing:

### Max fall speed reads as floaty
`PlayerController.MaxFallSpeed` is −20 m/s. A jump tops out around 5.4 m/s at touchdown (1.5 m
apex), so the clamp never binds on a plain jump — it only binds on long falls, where the body
stops accelerating and glides at 20 m/s (~72 km/h) for the rest of the drop. Real bodies
settle near 55 m/s, so long falls read as floating. Planned: raise the cap (−30 as a starting
point, tunable in the inspector). Not applied yet.

### The capsule does not follow the jump pose's feet
`Scenes/Player.tscn` gives the body a fixed `CapsuleShape3D` (height 1.79, offset 0.006, so
the bottom sits at −0.889) and `PlayerRig.RestHeight` measures exactly that as "the feet". The
standing alignment is correct — the soles sit at the capsule bottom (the water code measures
depth from `RestHeight` and reads right) — but the capsule never moves. When the jump pose
tucks the feet up inside it, the bottom stays at the standing sole line, the body lands while
the feet are still up, and the feet only reach the ground when the landing blend lowers them:
the hitbox touches down first, then the feet do. That is the reported "landing feels weird".

**Planned fix (not yet implemented):** the capsule bottom tracks the animated feet while
airborne — raised with the tuck, top fixed so head clearance is untouched — and walks back
down to the standing base on the ground, so the floor pushes the body up as the legs extend
instead of snapping. Measured from the LeftFoot/RightFoot bones (resolved in `PlayerRig`,
which currently resolves only head/shoulder/hand bones), less an ankle-to-sole offset.

**Eventual wish (noted, not scheduled):** "the hitbox should just be the model." A skinned,
animated mesh cannot be a collision shape in Godot; the practical path is a multi-shape rig
(capsules/spheres on bones updated to the bone poses) — a later change, for combat precision.

## Verification
None — no code changed, no build run. The diagnosis is read from the scene files and the rig
code; the fix will be verified by build and in-editor when implemented.
