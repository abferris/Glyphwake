## Fixed: `tools/fix_refs.sh` rewrote references belonging to other files

**Where:** `tools/fix_refs.sh`

**Symptom:** a basename containing a regex metacharacter — `MyTool+X.cs` — was matched with only
a partial escape, so `+` acted as a quantifier on the preceding character. Asking for
`MyTool+X.cs` silently matched (and rewrote) references to an unrelated `MyToolX.cs` instead of
the file actually being moved. The move looks successful while corrupting an innocent file.

**Cause:** the escape set did not cover `+`, `|`, `{}`, `(` and `)`.

**Fix:** escape every ERE metacharacter — `sed 's/[][\\.^$*+?(){}|]/\\&/g'`.

**Also added, both warning-only:**

- a warning when a moved `.cs` has no `.uid` sidecar next to it, since Godot then mints a fresh
  UID and every `uid=`-based reference to that script breaks;
- a post-pass warning listing any reference still pointing at the basename from a path other
  than its new home, which catches file types outside the rewrite set.

## Fixed: `tools/fix_refs.sh` was unusably slow on `/mnt/c`

**Symptom:** a single basename took 7.2s, so the 38-file reorg projected to ~4.5 minutes and
blew the 120s command timeout.

**Cause:** the script ran a full `find`/`grep` tree walk per basename, and `/mnt/c` (DrvFs) is
I/O bound — the same tree was re-walked 38 times.

**Fix:** the project tree is now walked once up front and indexed in memory, then reused for
every basename. Sandbox timing dropped from 7.2s to 0.018s; the full real-project run is ~2min,
dominated by the two unavoidable initial walks.

# Session 2 — glyphs are catalogued, so Player.tscn stops growing per glyph

## Todo status

`docs/future/CURRENT_TODO.md` unchanged — the rune setup menu and the remaining techniques are
still listed there, and nothing about them moved.

## The problem

`Scenes/Player.tscn` enumerated every glyph individually. Each new glyph cost three lines: an
`ext_resource` for the `.tres`, a `GlyphLoadoutEntry` sub_resource for its points, and — for a
technique — a `Technique = ExtResource(...)` export. The scene's length tracked the content and
had to be reopened every time a glyph landed. `PlayerTechniques.cs` was the worst of it: its
doc comment already said wall jump, air dash, waterbreathing and spiderclimb would each "get
their own export".

The underlying error was not file size. `GlyphLoadout.Entries` is *player-owned mutable state* —
points spent, to be saved — and it was being serialized into a static scene file.

## Added: `Scripts/Glyphs/Framework/GlyphCatalog.cs`

**Where:** `Scripts/Glyphs/Framework/GlyphCatalog.cs`, `Resources/Glyphs/GlyphCatalog.tres`

A `[GlobalClass] Resource` holding `Techniques` / `Actives` / `Passives` as three typed arrays —
the same "three typed lists, not one list with a kind field" reasoning already applied to passive
targets. `Player.tscn` references this one resource. `AllGlyphs()` flattens for enumeration;
`TechniqueWithTrigger(trigger)` answers a capability question.

The master catalog that a separate per-type file would have needed is deliberately **not** built:
nothing consumes "every glyph" until the rune setup menu does.

## Changed: points are seeded, not authored in the scene

**Where:** `Scripts/Glyphs/Framework/GlyphLoadout.cs`, `Scenes/Player.tscn`

`GlyphLoadout` gained `[Export] GlyphCatalog Catalog` and a `_Ready` that seeds any catalog glyph
with **no entry** from `Catalog.DefaultSeedPoints` (5) — the value the scene used to hardcode.
Seeding rather than assigning is what lets a restored save, or a deliberate zero, survive; new
`HasEntry()` exists because "no entry" and "an entry with 0 points" are different questions.
`Entries` stays exported for save/load.

## Changed: a technique is looked up by trigger

**Where:** `Scripts/Player/Data/PlayerTechniques.cs`

`[Export] TechniqueGlyphData Technique` became a plain settable property, defaulted in `_Ready`
from `Loadout.Catalog.TechniqueWithTrigger(TechniqueTrigger.Airborne)` only when nothing set it
first. So the second airborne technique is a catalog entry, not a new export. Settable because
`tools/test_glyph_loadout.gd` assigns the glyph directly instead of standing up a catalog.

## Godot finding: exported C# arrays lose their element type

Probed rather than assumed, and the assumption was wrong in two places.

`[Export] Array<SomeCSharpClass>` reaches Godot as `Array[Resource]`. `get_typed_class_name()`
reports `Resource`, and `GlyphCatalog.tres` saves with no type marker. A type written into the
file by hand (`Array[TechniqueGlyphData]([...])`) is **discarded on load**. Pushing from GDScript
is refused by Godot's typed-array check — but it refuses everything, including a correctly-typed
glyph, and `Actives` refused even its own type while `Techniques` and `Passives` accepted theirs.

So the typed arrays buy C#-side compile-time and cast safety and legible grouping, but **not** an
editor-side type filter. `GlyphCatalog.Validate()` is the substitute: it reports any glyph not in
its own subclass's list, plus null slots, and `GlyphLoadout` refuses to seed off a catalog that
fails. The negative case could not be constructed from GDScript (the arrays refuse the push), so
it is left to be confirmed in the editor when the first active glyph is authored —
`tools/test_glyph_catalog.gd` says so rather than pretending otherwise.

**Cause worth remembering:** assigning a GDScript literal (`catalog.Techniques = [glyph]`) to a
C# typed-array property replaces the array with an untyped one. `append()` mutates in place and
keeps it. `tools/build_catalog.gd` uses `append()` and asserts the type before saving.

## Added: `tools/build_catalog.gd`, `tools/test_glyph_catalog.gd`

The catalog `.tres` is generated through `ResourceSaver` rather than hand-written, because
hand-writing it means guessing the serialized form of the typed arrays — the failure mode above.
Re-run it after adding a glyph.

`tools/test_glyph_catalog.gd` covers: the catalog loads and holds the real `DoubleJump` resource
(not a copy); the documented `Array[Resource]` behaviour is pinned, so a Godot upgrade that fixes
it gets noticed; trigger lookup answers the right glyph and returns null for the three triggers
with no technique; `AllGlyphs` flattens; seeding produces one entry with 5 points; zeroing reuses
that entry rather than appending (`PointsFor` sums, so a duplicate would silently read double); a
loadout with no catalog still starts empty, which is the shape `test_glyph_loadout.gd` builds.

# Session 3 — the animation graph can no longer silently lose a clip

## Todo status

`docs/future/CURRENT_TODO.md` unchanged.

## Added: `tools/test_animation_clips.gd`

**Where:** `tools/test_animation_clips.gd`, guarding `Scripts/Core/AnimationIds.cs:124` and
`Scripts/Player/Animation/Movement/LocomotionGraph.cs`

`AnimationIds.ReachableClips` is a hand-maintained list of 16 clip names that
`PlayerController.BuildAnimationGraph` turns into the whole AnimationTree. The clips themselves
are generated — `tools/build_stickman.gd:97` writes `Scenes/Stickman.tscn` from the PolyOne FBX
— so the C# list and the generated library can drift apart, and nothing checked.

**Symptom it guards:** the drift was near-silent. `AddNode` creates a state whatever the name is,
so the graph still looks complete, and both `ClipLength` and `LoopModeFor` absorb a missing clip
(`anim?.Length ?? 0`, `?.LoopMode ?? Linear`). `AnimationIds.cs:20` records this having already
happened once: "renaming a clip in the AnimationLibrary broke locomotion silently".

**How the test reads the list without C# statics:** GDScript cannot access static members on a
`CSharpScript` (`Invalid access to property or key 'ReachableClips' on a base object of type
'CSharpScript'`), which rules out reading `AnimationIds.ReachableClips` directly. But
`LocomotionGraph.cs:118` names each state after its clip, so the built state machine *is*
`ReachableClips` reflected at runtime. The test instantiates `Player.tscn`, reads
`AnimTree.tree_root`'s node list and `Visual/Anim`'s `get_animation_list()`, and compares. That
also tests the real production path rather than a re-parse of the constant.

Asserts: every graph state names a clip the library has; state names are distinct (a rename
colliding with another reachable clip would collapse two states while the count still looked
right); the library has no clip called `Start` or `End`, which the state machine reserves as
virtual nodes. Library clips no state names are **reported, not failed** — `AnimationIds.cs:127`
documents Sitting, Yelling and the Backward clips as deliberately unreachable.

**Verified by deliberately breaking it:** two bogus names injected into `ReachableClips`, rebuilt,
test reported `FAILED` naming both, then reverted. A guard never seen to fail is not verified.

## Fixed: drift was reported N times, badly

**Where:** `Scripts/Player/Animation/Movement/LocomotionGraph.cs`

Added `MissingClips()` and one aggregated `GD.PushError` at the top of `Build`. The check uses
`HasAnimation`, not `GetAnimation`, because the latter logs an engine error per call.

**Why:** the only symptom before was one raw `Animation not found` per missing clip from whichever
lookup happened to touch it — naming neither the clip that is wrong nor the list it came from. Now
one error leads, naming all of them and both fixes ("fix the constant, or regenerate
`Scenes/Stickman.tscn` with `tools/build_stickman.gd`").

**Not changed deliberately:** the missing states are still built. One bad clip must not stop the
character animating the fifteen that exist, and skipping the node would also invalidate every
transition into it. Topology is byte-identical to before in the clean case.

`ClipLength` and `LoopModeFor` were left as they are: both are already null-safe on purpose, and
`IsValid`'s doc says the character "animates nothing rather than throwing".
